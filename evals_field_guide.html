Evals Field Guide

How teams test LLM applications and agents today, from a software-engineering angle, for a regulated RAG setup. It covers the tools and techniques, what's standardized, what teams actually do, and a hands-on lab: one app evaluated by four harnesses and four platforms, plus a live run on real OpenAI models.

Your situation

What your answers imply

Single-shot RAG with hypothetical-question indexing, plus some tool-using agents. It's a regulated corporate environment. Traces must not go to eval SaaS, but your own AWS/Azure tenants are fine. Domain experts can label as much as needed. You want all three levels: dev tests, SME exploration and labeling, and production monitoring with explainability.

level 1 · versioned with the app

Dev & CI evals

  • Golden set (JSONL), graders and judge prompts live in the same repo and PR as the app prompts.
  • Runner: pytest (optionally DeepEval metrics) or promptfoo. Nightly: real model, N trials, calibration check.
  • Judge endpoint inside your tenant: Azure OpenAI deployment or Bedrock model, pinned version.
level 2 · people in the loop

SME exploration & labeling

  • A self-hosted platform in AWS/Azure: Langfuse (MIT core, Helm/Terraform), Phoenix (ELv2, single container + Postgres) or MLflow (Apache-2.0; managed on Databricks or SageMaker).
  • SMEs label traces in annotation queues. Labelled items get exported to git as golden cases and judge-calibration labels.
level 3 · production

Monitoring & explainability

  • OTel GenAI spans from the app to the same self-hosted platform (or your APM).
  • The same judge runs on a sample of live traffic. Drift alerts. Failures feed back into level 2.
  • End-user explainability comes from citations to retrieved chunks. The full trace is for auditors and support.

RAG with hypothetical questions: what to measure

  • Retrieval, separately from generation. SMEs label the relevant chunk(s) per question. Measure recall@k / MRR. It's cheap, deterministic, and needs no judge.
  • Ablation Δ: run the same set with and without the hypothetical-question index. If recall barely moves, the trick isn't paying for itself.
  • Question generation quality (offline, at indexing time): sample generated questions and have a judge or SME check "answerable from this chunk".
  • Generation: faithfulness to the retrieved chunks, answers the question, correct refusal when nothing relevant was found, citation correctness.

Do agents change things? Mostly the same machinery, plus:

  • Grade the outcome (state or answer) plus a few hard trajectory rules ("must look up the order before promising a date"). Don't grade the exact step sequence.
  • Variance is higher, so run several trials and report pass^k.
  • Tools need fixtures or mocks and isolated state per trial.
  • Multi-turn agents need simulated users, and cost per case goes up by an order of magnitude.
Mental model

Evals are a loop, not a phase

Current practice is a closed loop. Real traces feed error analysis, which produces failure categories. Those become dataset cases and graders, which gate releases, which produce new traces. Anthropic's agent-eval guide and Hamel Husain and Shreya Shankar's courses describe the same loop.

Techniques

Three kinds of graders

Rule of thumb: use deterministic graders wherever possible, a judge for what code can't see, and humans to calibrate both. Grade the outcome (state, answer) more than the path. Over-specifying agent steps makes evals brittle.

cheap · fast · reproducible

Code-based

  • JSON schema / Pydantic validity
  • Exact or set match on labels (category, intent)
  • Tool called with the right args, trajectory constraints
  • Regex must-include / must-not (e.g. "prorated refund")
  • Outcome checks: DB row exists, test suite passes
  • Latency, cost, token budget
  • Retrieval recall@k against labelled relevant docs

Weak spot: brittle on valid paraphrases, and blind to meaning.

flexible · costs tokens · must be validated

LLM-as-judge

  • Groundedness / faithfulness to context
  • Policy: "never promises unsupported refunds"
  • Pairwise A vs B (prompt or model upgrades)
  • Reference-guided correctness
  • Trajectory review for agents
  • Conversation-level (multi-turn) goals

Weak spots: position, verbosity and self-preference bias. Also non-determinism and drift when the judge model updates.

gold standard · slow

Human

  • Open coding of traces during error analysis
  • Labels for judge calibration (≈100–200 per failure mode)
  • Annotation queues for sampled production traffic
  • Launch reviews of high-stakes flows

One domain expert as "benevolent dictator" beats committees for consistency.

RAG-specific

Evaluate retrieval and generation separately. Retrieval: recall@k and precision against labelled docs, or LLM-rated context relevance. Generation: faithfulness to the retrieved context, answer relevance. Ragas and DeepEval ship these metrics. In the lab, a plain recall check found a real lexical-gap bug.

Agents

Grade the final state in an isolated environment, and check the trajectory only for hard constraints (e.g. "must call lookup_order before promising a date"). Use simulated users for multi-turn (τ²-bench style). Run several trials and report pass^k. Isolate trials so state doesn't leak between them.

LLM-as-judge

Where the judge comes from, and how calibration works

Every tool needs you to supply a judge model

No mainstream eval tool ships a built-in local judge. Every LLM-graded metric calls a model you configure, and several default to OpenAI unless you change it:

promptfoo llm-rubricOpenAI by default. Set defaultTest.options.provider to any provider (Azure, Bedrock, Ollama…).
DeepEvalOpenAI by default, even for some deterministic metrics (seen in the lab). Pass model= (Azure, Bedrock, Ollama, LiteLLM, custom).
Ragas, Phoenix evals, MLflow judgesExplicit judge model or LLM wrapper.
Langfuse managed evaluatorsAn "LLM connection" you configure. Runs on the Langfuse worker, so the worker needs network access to your model endpoint.
Azure AI Evaluation SDKYour Azure OpenAI deployment (AzureOpenAIModelConfiguration).
Bedrock EvaluationsAWS-curated judge models with tuned prompts. External judges aren't allowed.

Small local judges do exist for narrow jobs. Vectara HHEM-2.1-Open (0.1B, Apache-2.0, CPU, ~1.5 s per 2k tokens) scores whether an answer is supported by its context. Patronus Lynx (open 8B/70B) and IBM Granite Guardian cover hallucination and risk checks. Prometheus 2 is a general rubric judge. They're useful as a cheap, private first pass on faithfulness, but they are "small" and need calibration like any other judge.

The lab's offline "fake judge" isn't a model at all. It's a word-overlap script, there only so the harnesses can run without a key.

Calibration: what it is, and what it isn't

No weights are tuned. Calibration means measuring how often the judge agrees with your experts, and then changing the things you control until the agreement is good enough. That makes it work the same for a closed model like GPT-5.x as for an open one. You treat the judge like any other measuring instrument and check it against a reference before trusting its readings.

  1. Label. SMEs mark ~100–200 real outputs per criterion as PASS/FAIL, with a one-line reason. Include hard cases.
  2. Split. Use a few as few-shot examples. Split the rest into dev (for iterating) and test (touched once, at the end).
  3. Run the judge on dev and compare against the labels. That gives a confusion matrix, from which you compute TPR, TNR and Cohen's κ.
  4. Read every disagreement. Then change the rubric wording, add few-shot examples, split one vague criterion into two binary ones, give the judge the evidence (context, tool results), or switch to a stronger judge model.
  5. Stop when TPR and TNR are both ≥ ~0.8–0.9 on dev. Report the numbers on test. That's the judge's certified accuracy.
  6. Pin and re-check. Pin the judge model version. Re-run calibration nightly and on any change to the judge model or rubric. Closed models change underneath you, and this is how you notice.

Worked example: turning a judge's score into a true rate

On the held-out test labels, suppose the judge's TPR = 0.90 (it passes 90% of truly good answers) and TNR = 0.80 (it catches 80% of truly bad ones). In production it reports 85% pass. The true pass rate is

true = (observed + TNR − 1) / (TPR + TNR − 1)
     = (0.85 + 0.80 − 1) / (0.90 + 0.80 − 1)
     = 0.65 / 0.70 ≈ 0.93

So the judge under-reports quality here. With TNR = 0.60 instead, the same 85% corresponds to ≈ 0.90. Always publish the corrected figure, with an interval from bootstrapping the labels. This is the Rogan–Gladen correction that scripts/calibrate_judge.py implements.

Judge design rules that make calibration pass

  • Binary PASS/FAIL, one criterion per judge. Avoid 1–10 "quality" scores.
  • The judge sees the evidence (retrieved chunks, tool results), not just the answer.
  • Reasoning first, then a verdict in strict JSON. Temperature 0 where the model allows it.
  • A different or stronger model than the app, to reduce self-preference.
  • Track judge cost and latency as CI metrics.

Landscape

Tools, as of September 2026

There are two layers. Frameworks and runners execute evals in code or CI. Platforms store traces, datasets and experiments and add UIs, annotation and online evals. A third group is vendor-native: evals built into a model or agent product. Most teams end up with one framework and one platform. Cards marked "tested" were run hands-on in the lab.

Versions and licenses come from the PyPI/npm registries on 24 Sep 2026. Corporate news comes from primary announcements (see Sources). Popularity rankings in blog round-ups are mostly vendor SEO, so treat them with care.

In the wild

What teams actually do

Given the same data, graders and judge model, every tool here produces the same verdicts. The lab showed that across nine adapters. So the real choice is about workflow, governance and who uses the results. That's what these patterns cover.

52%run offline evals on test sets
37%run online evals on production traffic (45% of those with agents in prod)
60%rely on human review
53%use LLM-as-judge
89%have some observability; 62% have step-level tracing

LangChain "State of Agent Engineering", n = 1,340, surveyed Nov–Dec 2025. It's a vendor survey, so the sample leans toward LangChain users. The DataTalks.Club 2025–26 community survey is more sobering: 31% don't evaluate at all and only 17% have automated evaluation.

Pattern 1: Platforms are APM for LLMs, plus a labeling workbench

Your ELK/APM analogy holds. Langfuse, Phoenix, LangSmith and MLflow are mostly used for tracing, cost and latency dashboards, debugging, annotation queues, and turning production traces into datasets, plus online evaluators on sampled traffic. They do ship experiment runners and CI hooks (Langfuse experiment-action, Braintrust's GitHub Action), and eval-first teams, especially Braintrust users, do gate releases through them. The common setup, though, is a code-first harness as the release gate and the platform alongside it. It complements regression tests the way APM complements performance tests. It doesn't replace them.

Pattern 2: Keep the version-control concern front and centre

Some sources argue for a prompt registry (Langfuse prompt management, MLflow prompt registry): versioned prompts with metadata and runtime updates without a redeploy. The risk is exactly what you flagged: prompts, judges and datasets drift away from the code they test. The pattern that holds up in regulated settings:

  • git is the source of truth for app prompts, judge prompts, rubrics and the golden set, all changed in the same PR.
  • CI publishes to the platform (prompt versions, dataset snapshots), tagged with the commit SHA. Nothing is edited only in a UI.
  • Labels collected in the platform get exported back to git through a reviewed PR.
  • If a registry is used at runtime, the app pins a prompt version. No "latest".

Pattern 3: Cloud-native evals

If you're on AWS or Azure anyway, the clouds now ship evals that keep data in your tenant.

  • Amazon Bedrock Evaluations: automatic, LLM-as-judge and human jobs, plus RAG evaluation (retrieve-only or retrieve-and-generate). Accepts bring-your-own responses from a non-Bedrock RAG. JSONL in S3, ≤ 1,000 prompts per job, custom metrics. The judge models are AWS-curated.
  • Azure AI Evaluation SDK (azure-ai-evaluation 1.18.7): evaluate() runs locally or in CI with your Azure OpenAI deployment as judge. It has groundedness, relevance, retrieval, agent and safety evaluators, and can log to a Foundry project.

Pattern 4: Tiered cost

  • Deterministic checks on every PR (free).
  • A small or local judge (HHEM-style) as a first pass. A big-model judge only for disputed or high-risk cases.
  • Nightly: full set, N trials, judge calibration.
  • Production: 1–10% sampling, 100% only for high-risk intents.

Pattern 5: Error analysis before metrics

Practitioners (Hamel Husain & Shreya Shankar, Anthropic's agent-eval guide) agree on the order: read ~100 real traces, name the failure modes, and only then write graders for those failure modes. Off-the-shelf "helpfulness" and "coherence" scores rarely move decisions. Teams report spending 60–80% of AI dev time on evaluation and error analysis.

Pattern 6: Hosted eval features come and go

OpenAI launched hosted Evals in 2025 and is shutting it down on 30 Nov 2026, together with Agent Builder and the reusable Prompts API. Promptfoo moved to OpenAI and Langfuse to ClickHouse in the same year. Datasets, graders and prompts that live only inside a vendor's product are migration work waiting to happen. This is the strongest practical argument for keeping them in git.

Platform & vendor evals

Same idea, three different homes

"Evals" means three different things depending on where you get them. The lab ran the same golden set through each family: Phoenix, Langfuse, Braintrust and LangSmith and MLflow runners locally, and the OpenAI Evals API live. That made the differences concrete.

you own the runner

Code-first harnesses

pytest, promptfoo, DeepEval, Inspect. Evals are files in your repo, run by a CLI, and they fail the build. The result is a pass/fail verdict per commit.

Unit: your app or function · Graders: your code · Gate: exit code

evals as data + UI

Observability platforms

Langfuse, Braintrust, LangSmith, Phoenix, MLflow. Datasets, experiments and scores live in a shared service next to production traces. The result is a comparison over time, which people browse, annotate and discuss. The same judge also runs online on sampled live traffic.

Unit: experiment vs baseline · Graders: SDK code or UI-configured judges · Gate: extra step

vendor-native

Model and agent vendors

Cloud and model vendors ship evals inside their products: Amazon Bedrock Evaluations, the Azure AI Evaluation SDK / Foundry, and the OpenAI Evals API, which shuts down on 30 Nov 2026. Judges and graders run in the vendor's environment, and results live there too.

Unit: dataset of prompts or your uploaded responses · Graders: vendor evaluators + custom rubrics · Gate: poll job / parse results

How platform evals differ from test-suite evals

  • Every eval item is a trace. A low score links straight to the full trace (retrieval, tool calls, prompts). In a plain CI log you only get the assert message.
  • Experiments get compared, not just passed or failed. Runners report scores and exit 0 (in the lab: Langfuse, Braintrust and Phoenix all exited 0 on the broken v2). Gating is a separate step: a run-level evaluator plus a threshold script, Langfuse's experiment-action (raises RegressionError), or Braintrust's CI integration.
  • The same judge runs online. Langfuse runs LLM-as-judge evaluators server-side on production observations with filters and a sampling rate. LangSmith, Braintrust and MLflow have equivalents. This is the main thing a pure test suite can't do.
  • Non-developers take part. Annotation queues, a prompt playground and dataset editing let domain experts label and compare without touching git.
  • Risk: graders that live only in the UI. A judge prompt edited in a web form isn't code-reviewed or versioned with the app, and it drifts. The pattern in the lab: keep graders in code (evals/judge.py) and push the scores to the platform.

OpenAI Evals API shutting down 30 Nov 2026

Deprecated. OpenAI announced on 3 Jun 2026 that it's winding down the Evals platform. Existing evals become read-only on 31 Oct 2026, and the dashboard and API shut down on 30 Nov 2026, including the graders documented for eval workflows. Agent Builder and the reusable Prompts API go on the same day. OpenAI's recommended path is promptfoo, which it now owns. Don't start new work on it. It's kept here because the concepts carry over to other tools.

Evals are server-side objects. An eval holds the item_schema and testing_criteria (graders). A run supplies data and, optionally, a model plus a templated prompt ({{item.ticket}}, {{sample.output_text}}). Results appear in the dashboard or through runs.output_items.

  • Grader types: string_check, text_similarity, python (sandboxed code), score_model, label_model, multi. The same grader objects are used for reinforcement fine-tuning.
  • Hosted mode tests a prompt and model. OpenAI generates the samples, so your retrieval, tools and code aren't involved. Bring-your-own-output mode uploads JSONL items that already contain your real app's answer, so hosted graders score your app. The lab script does both.
  • Agents: trace grading in the dashboard applies graders to Agents SDK traces. The older open-source openai/evals registry is legacy.
  • Fits: OpenAI-centric stacks that want zero eval infrastructure. Watch for: data leaves to OpenAI, judge models are OpenAI-only, there's no local runner or exit code (you poll the run), and it's weak for multi-provider apps.

Lab, live: bring-your-own-output runs scored v1 11/12 and v2 9/12. Your app's outputs go in the item ({{item.output}}) with include_sample_schema: false.

Cloud-native evals: AWS and Azure

These fit your constraint that traces can't go to eval SaaS but can go to your own cloud tenant.

  • Amazon Bedrock Evaluations offers automatic, LLM-as-judge and human jobs. For RAG it has retrieve-only and retrieve-and-generate jobs with metrics such as correctness, completeness, faithfulness, citation precision and coverage, plus custom rubric metrics. You can bring your own responses from a RAG that doesn't run on Bedrock. Jobs are async: JSONL in S3 (≤ 1,000 prompts), IAM service role, optional KMS. For CI you create the job, poll it, then gate on the S3 results. Judges are AWS-curated models.
  • Azure AI Evaluation SDK (azure-ai-evaluation) is a Python library. evaluate(data, target, evaluators) runs locally or in CI, and your Azure OpenAI deployment is the judge. It includes groundedness, relevance, retrieval, response-completeness, agent (intent resolution, tool-call accuracy, task adherence) and safety evaluators. It can log results to a Foundry project. It's the closest thing to DeepEval inside the Azure boundary.
  • Both work well as the judge and runner inside your tenant. The golden set and gating logic should still live in your repo.

0.767Inspect mean reducer over 5 epochs

A single CI run would pass or fail at random. Pick the metric that matches the product. For a support bot, users feel pass^k. For "generate 5 options, a human picks one", pass@k is fine.

Findings the evals surfaced while building the lab

  • A real retrieval bug. "I was charged twice" never retrieved the refund doc ("Duplicate charges…"). The citation check caught it on the first run. RETRIEVER=naive reproduces it.
  • Wrong doc chosen. The answerer cited the pricing doc for a double charge because the planner picked the top-ranked doc rather than the relevant one. That's a classic groundedness-vs-relevance gap.
  • OTel interop is partial. Phoenix accepted the GenAI semconv spans and recognized the agent span. Its input/output columns stayed empty (it expects OpenInference attributes), and the evaluation event showed up as a raw span event, not as a Phoenix annotation.

Architecture

Reference architecture

The design principle is to own the core (dataset, graders, judge prompts) as code in the repo and treat runners and platforms as replaceable adapters. Emit OTel so traces aren't locked into one vendor.

Where evals run

  • Inner loop: dev runs the subset for the feature they're changing
  • PR: deterministic and cheap, blocks merge
  • Prompt or model change: real model + judge + thresholds
  • Nightly: trials, calibration, A/B comparisons
  • Online: 1–10% sampled judging, alerts on drift

Cost control

  • Cache LLM responses keyed by prompt + model for unchanged cases
  • Only the judge tier costs real money. Use a smaller judge for triage and a larger one for disputes.
  • Sample production. Judge 100% only for high-risk intents.
  • Track the judge's cost per run as a CI metric

Governance

  • Dataset owner + review for label changes
  • Pin model versions and re-baseline on upgrade
  • PII policy for captured prompts (content capture is opt-in in OTel)
  • Eval results linked to commit, prompt version and model id

Recommendation for your setup:
  1. Golden set, graders and judge prompts in git, run by pytest (or vitest). Deterministic checks on every PR. A real-model judge on prompt changes and nightly, with N trials and pass^k.
  2. The judge model is a pinned Azure OpenAI or Bedrock deployment, calibrated on SME labels (100–200 per criterion, held-out test split), and re-checked nightly.
  3. One self-hosted platform on AWS/Azure for traces, SME annotation and sampled online judging. Langfuse is the most complete, but runs four stateful services. Phoenix is the lightest. MLflow is best if you're on Databricks or SageMaker. Labels flow back to git through PRs.
  4. Add promptfoo later for model upgrades and red-teaming (it has a language-agnostic CLI, which suits your .NET side).
  5. First step before any tooling: error analysis on ~100 real traces with an SME.

Open questions

What still needs deciding

Your answers settled the stack language, where traces may live (your own AWS/Azure tenants, not SaaS), label availability and the three levels. These are still open:

Which judge endpoint is approved?Azure OpenAI, Bedrock, or both? Pin a model version and decide who approves judge upgrades, since each upgrade needs recalibration.
What may traces contain?PII and content-capture policy, retention, and who may read raw prompts. OTel content capture is opt-in per deployment.
Who owns the golden set?A named SME owner. The review path from platform labels to git PR. How often cases get added from production failures.
What does "explainability to end users" mean?Citations to source chunks, a confidence indication, or an auditable trace? It changes what you log and which graders you need (e.g. citation correctness).
Which failures are expensive?False promises, wrong figures, PII leakage, prompt injection through documents? These get deterministic guards and red-team suites, not only judges.
What's the CI budget?Tokens and minutes per PR and per night decide trial counts and when the big judge runs.
Does the hypothetical-question index pay off?Run the retrieval ablation (with and without it) on SME-labelled relevance as the first real experiment.

Claude Code: evals for skills and plugins

claude plugin eval shipped on 11 Sep 2026 (CLI ≥ 2.1.269). A case is a folder: prompt.md (a realistic user request plus limits and allowed tools) and graders/*.md. Each case runs in an isolated, headless session, 3× with the plugin and 3× without. The report shows WITH, W/OUT and Δ, meaning what the skill actually adds.

  • Free graders: regex, tool_used (e.g. "the Skill tool fired"), tool_order, file_exists. Paid judge graders: llm (best 2 of 3 votes) and baseline (at least as good as a reference transcript). There are no custom-code graders.
  • MCP servers can be mocked with fixed or agent-played answers. --threshold, --max-cost-usd and --json are for CI. Exit codes: 0 pass, 1 below threshold, 2 partial (cost cap). claude plugin eval init drafts the suite for you.
  • A second route: the skill-creator skill keeps a separate evals/evals.json (prompt, expected output, expectations). It runs with-skill and without-skill subagents, grades them, and benchmarks mean ± stddev of pass rate, time and tokens. It then shows outputs in a review viewer for human feedback. It also optimizes the skill description for triggering, using ~20 should-trigger and should-not-trigger queries with a 60/40 train/test split.

What the skill eval showed

  • Without the skill, the agent made things up. For "do you ship to Canada?" the baseline answered "Yes, we do ship to Canada. Standard shipping typically takes 5-7 business days". The judge voted FAIL 3/3. With the skill: "we only ship to the EU, UK, and Switzerland", PASS 3/3.
  • The baseline asked instead of acting. On the cancellation case it asked for the refund policy. That's reasonable behavior, but it failed the task. Δ measures exactly this kind of value added.
  • Trigger precision: an unrelated coding prompt didn't fire the skill in either arm (tool_used … min 0 max 0, arm: both). The skill-fired check is reported as an indicator rather than scored, which keeps Δ honest.
  • Worth borrowing for your apps: run every eval against a baseline without your RAG, tool or prompt change. A high score with Δ ≈ 0 means the feature isn't what makes it pass.
